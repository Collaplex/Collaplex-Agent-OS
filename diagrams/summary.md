## 〇、一句话总纲

**北极星：无显式上下文窗口的 Agent 交互体验。**
用户感觉不到窗口存在——不压缩、不遗忘、不降智、不卡顿。
路径：**程序管记忆，模型管推理**；从"靠模型自己撑上下文"变成"靠程序组装上下文"。

## 一、起点：标签 vs JSON（结构化输出）

| 方案 | 对模型 | 对系统 | 结论 |
|---|---|---|---|
| 纯 Markdown/标签 | 好写、小模型稳 | 有歧义、难嵌套、难校验 | 不用于生产核心 |
| 纯 JSON | 小模型易崩（引号/逗号/转义） | 好解析、好校验、好传输 | 需约束解码兜底 |
| **展示 MD + 后台 JSON** | 两头兼顾 | 工具调用/Structured Outputs 产 JSON | ✅ 采用 |
| 末尾挂唯一标记 JSON 块 | 自然 | 前端匹配标记头即停渲染 | 可用，但要防坑 |

**折中方案的四条铁律**（末尾标记块）：
1. 标记要独特（`<!--AGENT_META_V1` 而非 ```json，防正文代码块误判）
2. 流式要缓冲（处理 `` / ``` / ```j 的中间态）
3. 截断要处理（标记有头无尾 → JSON 不完整，别崩）
4. 指令给例子（小模型"给示例"比"讲描述"有效）

**JSON 出错的解法不是退回标签，而是约束解码**：OpenAI Structured Outputs / llama.cpp GBNF / vLLM guided decoding / Outlines / XGrammar。

## 二、上下文窗口的本质（KV 复用）

- **应用层不能直接"给 KV"**，只能改 prompt；KV 由推理引擎按 prompt 前缀算出。
- **复用只认前缀**：追加式可复用但窗口会爆；替换式省窗口但 KV 全废——根本矛盾。
- **双缓冲 KV**（两轮窗口 → 推理与检索重叠）：思路成立，但显存翻倍、需引擎层支持，主流框架（Hermes/DSH）都没做。
- Hermes/DSH 现状：异步预取 + 稳定前缀，但**无双缓冲**，且框架层碰不到引擎内部 KV。
- 学术对应词：**认知外部化（Cognitive Externalization）**；相关原型 SCD / JLC / LLMFS / Memori。

**外部程序管上下文的五种手法**：滚动摘要 / 结构化状态 / 分段按需加载 / 历史 RAG / 任务栈状态机。

**16k 窗口预算示例**：固定 system+skill 2k · 状态摘要 1k · RAG 3k · 最近 1~2 轮 2k · 当前问题 0.5k · 输出预留 3.5k。

## 三、三代演进（踩坑史）

| 代 | 核心思路 | 结果 | 教训 |
|---|---|---|---|
| **第一代** | 上百节点超级状态机，穷举所有路径 | **炸** | 用确定性模拟不确定性 → 路径组合爆炸、异常分支无法穷举 |
| **第二代** | RAG 模拟状态机（二层热 RAG + 三层冷 RAG + 30s 异步归档 + 声明式获取） | 本地小模型**未开思考 BFCL 94%** | RAG 承担三职（记忆/知识库/日志）→ 写入放大、检索噪声、流程线性、定时脆弱、无权限隔离 |
| **第三代** | **Agent 就是 OS** | 预期更强 | 不预判，让模型在有限状态里自己选 |

**第二代原始设计流程**（记录在案）：
`注入默认skill → 判断解法 → 写二层热RAG → 声明取RAG → 注入思考skill → 思考方向 → 写RAG → 声明取RAG → 注入skill → 规划第一步 → 声明执行 → 专项模型执行 → 写RAG → …… → 输出结果 → 全量写RAG → 二层写三层冷RAG并标记 → 30s 无新问题则异步处理未入库数据 → 等下一轮`

**已埋下第三代的种子**：冷热分层、异步归档、声明式获取。

## 四、第三代架构：Agent 就是 OS

> 第二代是"**给程序加 OS 概念**"（装饰）；第三代是"**把 Agent 写成 OS**"（骨架）。

### 4.1 OS 映射

| OS 概念 | 第三代实现 |
|---|---|
| 内核 | 生成器 + 状态管理 + 权限控制（常驻，不随对话变） |
| 进程 | 主线 / 二线 / 三线（独立调度、独立超时回退） |
| 内存 | 上下文窗口（生成器统一分配/回收/换页） |
| 文件系统 | SQLite + 向量库 + 时间线（持久化） |
| 驱动 | Skill / 工具 / API（统一接口，即插即用） |
| 系统调用 | 模型声明需求 → 内核解析执行 |
| 用户态 | 输入输出 |

### 4.2 生成器 = 上下文治理引擎（核心支柱）

**不是造 Skill 的工具**，是"管上下文的操作系统"，管四件事：

1. **权限分级**：只读（核心指令/工具定义/冻结 Skill）· 模型可写（状态增量/时间线）· 程序注入（RAG/Skill 索引）· 模型可选（从候选里选）。模型输出若改只读区 → 直接拒绝。
2. **位置排序**：只读区最前（缓存永久命中）→ 程序注入区（从变化点重算）→ 当前问题（代价最小）。
3. **窗口预算**：算账 → 总窗口 − 输出预留 − 只读区 = 剩余可用，再按优先级精确分配，**不是"尽量塞"而是"按预算分"**。
4. **内容生命周期**：谁常驻、谁每轮更新、谁滑动窗口、谁用完即走。

### 4.3 三层流水线

```
三线（小模型 + LoRA）：路由、参数填充、清洗
   ↑ 结构化片段
二线（小模型/规则）：筛选、排序、校验、格式化
   ↑ 精炼资料包
主线（API/大模型）：推理、决策、生成
```

- 越靠底层，任务越稳定 → 缓存命中率越高。
- 三线可用 **LoRA 训动态工具路由**（专精窄任务），主线不再浪费 token 试错。
- 坑：延迟叠加（底层用规则/小模型）、信息丢失（每级留回溯 ID）、同步复杂（每级超时回退）。

### 4.4 模型分层

- **本地完整 agent = 3B 路由小模型 + 8B Qwen3-VL（主线）+ 向量模型**。
- **主线可切 API**：解锁更大窗口（128k~1M）、更强能力、模型无关（今天 GPT，明天 Claude）。
- 本地模式"省着用"，API 模式"敞着用"——同一生成器，两套预算策略，改配置不改架构。
- 纯音/峰值类失真提示：API 模式省的是 token 和延迟，不是算力。

### 4.5 上下文分区 ≈ 磁盘分区

| 分区 | 磁盘类比 | 内容 | KV 行为 |
|---|---|---|---|
| 🔒 只读区 | C 盘 / **外圈磁道**（线速度快） | 核心指令、工具定义、冻结 Skill | **永久命中，零重算** |
| ✏️ 读写区 | D 盘 | 状态增量、时间线 | 从变化点重算 |
| 📥 按需区 | U 盘 / 网络盘 | RAG 结果、Skill 全文 | 每次重算，用完即走 |

**铁律：只读区绝不能放在动态区后面**。否则等于把系统盘塞进内圈，每次提问全量重算。

### 4.6 三个工程原则

- **权限隔离**（防呆）：状态只能走 `apply_delta` 修改；驱动只读；单向数据流。
- **分级管理**（防乱）：内核只调度；编排层只做流水线；执行层（Worker）无状态、随叫随到。
- **驱动解耦**（防死）：统一窄接口 `execute(input)->output` / `generate(prompt)->text`；依赖注入换模型。

**落地节奏**：先单文件 MVP → 逻辑解耦、物理内聚（同类不同进程不拆微服务）→ 依赖注入 → 五条底线：**插件薄、接口窄、流水线可观测、先单后多**。

### 4.7 认知与计算分离

模型**不自己算**，只思考"计算方法" → 声明方法 → 工具线程调用真实程序执行 → 返回结果。
- 模型是策略家不是计算器；计算下沉到确定性程序（`math.sqrt()` 不会错）。
- 计算方法库即"系统调用表"；参数校验、超时、中间结果回传都在工具线程。

### 4.8 持久会话（外部工具当"设备"而非"一次性函数"）

- SSH/ComfyUI 会话**长持不断**，像人一样连续操作（有历史、环境变量、工作目录）。
- 环境描述只注入一次 → 省下大量重复 token；逻辑性来自连续状态。
- 会话即"文件描述符"，内核管生命周期，模型只发高层指令。

### 4.9 Skill 生态

- 外部公开仓库（数万 Skill）+ 本地运行时生成 → 能力无上限、兼容性好（绑接口不绑实现）。
- 守则：接口窄、生成器白名单、检索分级、执行隔离（沙箱）、版本锁定。

## 五、收益

| 维度 | 传统框架 | 第三代 |
|---|---|---|
| 压缩 | 模型总结，烧 token（**压缩税**） | 程序归档，零 token |
| 工具调用 | 模型试错，错误污染上下文（**试错税**） | 三线路由一次命中，错误不进主线 |
| 每轮 token | 随轮数线性膨胀 | 恒定（状态摘要 + 最近 1~2 轮 + 按需检索） |
| 有效 token 占比 | ~30~40%（其余管自己） | >90%（用于解决问题） |
| 10 元 token | ~30 轮 | **60~100 轮**（保守翻倍） |
| 上下文体验 | 聊几轮就压缩、滚雪球降智/遗忘 | 无感、连续、稳定 |
| 可移植性 | 绑 Linux（/proc、epoll、inotify） | 平台无关（SQLite/asyncio/HTTP，内核绑接口） |

**结论**：不是省吃俭用，是**架构差异带来的结构性成本优势**——压缩税、试错税、噪声税三税归零。

## 六、落地路线（先点亮屏幕）

1. **单文件 MVP**：跑通一轮对话（状态可硬编码、模型可 API）。
2. **装文件系统**：接上 SQLite，跑通 50 轮不崩。
3. **加载第一个驱动**：三线路由跑通，看命中率/准确率。
4. **最后补 UEFI**：配置、自检、驱动注册表、watcher。

> 不要一上来写 UEFI；先让内核进命令行，再补引导。
> 验证重点不是"能不能跑通"，而是：解析稳定性 / 状态一致性（50 轮漂移？）/ 检索准确性 / 上下文长度 / 错误恢复。

## 七、关键认知 / 坑表

- **小模型不差，是被用错了地方**：路由/参数填充/清洗给它，推理给大模型。主流"单模型对单任务"评测天然让小模型吃亏。
- **Agent 框架的能力断层**：Agent 框架（Hermes/DSH）跑在推理引擎之上，碰不到引擎内部 KV——应用层做不到真正的双缓冲。
- **压缩滚雪球的根源**：让模型管理它自己的记忆。模型不知道什么重要、什么以后要用。
- **认知落差**：大众只知道"AI=聊天框"（应用层），你在造"聊天框背后的认知引擎"（系统层）。GitHub 访问不了的人是"潜在用户"不是用户。
- **开源 1% 法则**：99% 使用者 / 0.9% 外围贡献者 / 0.09% 核心维护者 / 0.01% 架构定义者。
- **过度设计陷阱**：第一代 100+ 节点状态机、Boot+看门狗+内核+PgSQL 的多进程 OS 全砍 → 单进程 + 几个类 + SQLite，工作量降 70%。
- **评估引擎的三层框架**（老板旧标准）：物理推演是否正确 / 皮层裁决是否诚实 / 符号接地是否完整，任一断链即失败。
