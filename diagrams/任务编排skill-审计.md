## 0. 先复述你的图（有错立刻纠正）

```
                    调用
                     ↓
        ┌──→ 循环开始
        │      ↓
        │   获取任务单条
        │      ↓
        │   是否结束编排 ──yes──→ 生成任务清单
        └──no──┘                      ↓
                                   载入清单
                                      ↓
        ┌──────────────→ 执行序列 ────┘
        │                  ↓
        │     按顺序载入未完成的任务一条 ←──┐
        │                  ↓              │
        │           确认是否完成 ──no─────┘
        │                  │yes
        │                  ↓
        └─────no──── 是否全部完成
                           │yes
                           ↓
                        返回结果
```

一句话：**先编（一条条攒任务，攒够了收），再跑（逐条执行、逐条确认），全完成才返回**。

三条判断的去向（图上标了）：
- 是否结束编排：yes → 生成任务清单；no → 回循环开始
- 确认是否完成：yes → 是否全部完成；no → 回「按顺序载入未完成的任务一条」
- 是否全部完成：yes → 返回结果；no → 回执行序列

## 1. ❗ 照字面做会踩坑的（5 条，按严重度排）

### ✅1.（已拍）「确认是否完成」由**主 agent** 判
- 老板定：**判断交给主 agent** —— 这条判断不外包给执行体。
- 保留一条硬规矩：**干活的模型不许自判自己**。exec 干完把「这一步的判据 + 真实产出」交回主 agent，主 agent 对着判据说完成没完成。
- 判据要写进清单那一条里（不是临场想）；能程序验的（退出码 / 文件在不在 / 命令回显 / skill 自检）优先用程序验的那部分当依据 —— 仓里现成口味见 `main.py:779`「它没真跑过命令, 产出不算话」。

### ❗2. 「确认是否完成 --no--> 回上一条」**没有上限** —— 同一条无限重试
no 那条回环图上是裸的，没有"第几次了 / 超了怎么办"。
- 建议：每条带 **重试上限（默认 2 次）**，超了标 `卡住`、**停**（不静默跳到下一条），把选择权交回主 agent（换做法 / 拆细一点 / 跳过 / 放弃）。
- 这跟定时那条规矩一致：**不悄悄降级，把可选项摆出来**。

### ❗3. 一次性生成清单后**没有重策划回环** —— 计划错了没救
图从「生成任务清单」出去就再也回不去了。执行到第 3 步发现"这活根本不是这么拆的"，只能硬着头皮往下走。
- **你上一代管线有这一支**：`~/tools/stage_agent.py:6` —「可修复错误→RETRY_PLAN(<=3)」，98–115 行就是那张重策划提示词。现在这版把它丢了，等于**退化**。
- 建议：加一支 `要不要重策划？` →（是）回「生成任务清单」，**上限 3 次**（跟你上一代对齐），重策划时**已完成的那几步不许丢**（带回清单原文让它改）。

### ✅4.（已拍）清单**落冷库**（PG 另开一张表）
- 老板定：清单落盘，**放冷库的另一张表**（现在库是 `collaplex_rag`，里面只有 `rag_chunks` / `search_corpus` / `search_hot` 三张）。
- 建议表名 `orchestra`，字段照 Hermes 那张面板的形状：
  `id / 对话id / 序号 / 说明 / 做法 / 判据 / 状态 / 重试次数 / 产出 / 起止时刻`；
  状态：`未开始 → 进行中 → 完成｜卡住｜跳过`。
- 落库时机：**每步开始写一次、结束写一次**（断电最多丢一步的状态，不是整单）。本地那份 `state/orchestra-<进程键>.json` 仍建议留一份当"原文备份"（见 §7）。

### ✅5.（已拍）**阻塞式** —— 就是主 agent 自己那张活儿单
- 老板定：**用阻塞式**，形状参照 Hermes 那张待办面板（`任务 1/7` + ✅/◌/○ 三种状态 + 📦 后台任务折叠）。
- 含义：编排就是**主 agent 自己的任务**，一条一轮地往前推，全过程在这一轮里跑完，进度实时可见。
- ⚠ 前提见 §5 的「新查出来的前提」—— 现在一轮只允许起**一个** exec 任务，要接通才行。

## 2. 🟡 图上没写、得先定下来的（结构）

### 🟡6. 「结束编排」的判据谁给
「获取任务单条」这个循环靠它退出，但谁判"够了"没写。可能是模型说够、可能条数到上限、可能是你喊停。
- 建议：**模型说够 或 达到条数上限** 二者谁先到算谁（上限见 §4）。

### 🟡7. 一步到底是谁去干
图上每步只写"任务"。是**exec 带手跑命令**，还是**再挑一个 skill**？
- 建议：**一步 = 一次 exec 任务**（一次"声明"跑几条命令）。理由是你定的审计粒度——「一个一个来方便审计」；两步塞一次，出错时说不清是谁的锅。

### 🟡8. 中断 / 幂等：跑到一半断了怎么办
第 3 步命令跑了一半断电 / 被撤。重启后「按顺序载入未完成的任务一条」会不会把**做了一半**的那步当没做重来？
- 建议：清单里每条先写 `判据`，续跑的判据 = **先看一眼现状（判据成立就不重做）**；状态是 `进行中` 的那条要单独报出来问一句，别静默重做（有的步骤重做是有副作用的）。

### 🟡9. 「返回结果」返回什么
- 建议：清单全文（带每步状态）+ 一段小结（完成 N 条 / 卡住哪几条 / 各自的产出在哪）+ **卡住的单独列**。

### 🟡10. 谁调用它（决定实现形态）
从「调用」开始，但没写是**主 agent 挑 skill 调**、还是**框架来驱动**。
- 这条要定，因为它决定代码长在哪：定时最后是**两件套**——`skill/timer`（干活的）+ `定时.py`（框架接缝）。
- 建议同款：`skill/orchestra`（清单与执行）+ 根目录接缝（开场推一步 / 阻塞式等待），web 与 CLI 共用。

### 🟡11. 失败停机策略
一条卡住之后：整单停，还是跳过继续？
- 建议：**停**。编排里静默跳过失败步是最危险的（后面几步可能都建立在它成立之上）。

## 4. 我定档的参数（不认可的划掉）

| 项 | 我定的 | 为什么 |

| 清单条数上限 | **20 条** | 跟定时的最多 20 条对齐；超了报回让主 agent 拆批 |

## 5. 两条已拍 + 一条新查出来的前提

### 已拍（老板 2026-10-09）
- **时间形态 = 阻塞式**：编排就是主 agent 自己的任务，在这一轮里一条一条推完，进度实时可见（形状照 Hermes 那张待办面板：`任务 N/M` + ✅/◌/○ + 📦 后台任务）。
- **判断归主 agent**：每步完成与否由主 agent 判（干活的模型不许自判自己）。

### ⚠ 新查出来的前提：**现在一轮只允许起一个 exec 任务**
- 证据：`main.py:795` — `continue  # 这轮活由 exec agent 干完了, 不再让主 agent 自己答`。exec 干完这一轮就结束，回去等下一次用户输入 → **7 步的清单推不下去**。
- **好消息：这条通道已经有了，不用新造**：主循环第 686 行就是「开场注入」——
  `到点的提醒 = 定时.取待办()` → 有待办就**不等用户敲字**，直接把它当这一轮的输入交给主 agent。
  定时"到点叫醒"走的正是这条（CLI 与 web 都验过）。
- 所以编排照抄这条就成：**每步做完往"待注入"里放一条（第 N 步做完了 + 产出 + 下一步），框架立刻把主 agent 叫回来推下一步**，用户全程不用敲字。
- 落地形态（跟定时同款两件套）：
  1. `skill/orchestra`：清单 CRUD（写 / 读 / 推进度 / 落盘）。清单字段照 Hermes 那张列表的形状：`id / 内容 / 状态(/ 子项)`。
  2. 根目录接缝：开场注入 + 阻塞等待。**建议把「待注入」这层抽出来共用** —— 定时与编排各写各的条目，`取待办()` 统一取（否则两套通道会互相抢）。

## 7. 三库与断点续干：查过的现状（哪些能复用、哪些要新建）

老板要的形状：**一个原文备份 + 一个清洗后 + 一个运行内存库（放还在清洗的事件）** → 断电不丢、能断点续干。

### ✅ 已经有的（复用，别另造）
| 现成物 | 在哪 | 实测 |
|---|---|---|
| **原文备份** | PG `rag_chunks` 的 **tier 1**（24244 行 / 1105 个来源，样例 `('实验-20260928-01','对话','用户','路由器放哪里了…')`） | 一层就是原文那一档，已经在库里 |
| **清洗后** | 同表 **tier 2**（21919 行 / 467 来源，来自 `corpus/hermes-history/*.md`）+ **tier 3**（1957 行，kind=知识 1690 / 概述 267） | 对话层 + 精炼层，两档分开 |
| 原文语料文件 | `skill/rag/corpus/hermes-history/*.md` | refine 的输入源 |
| **幂等重扫（隐式断点续干）** | `refine.py:328` `hash = sha256(text)[:16]` | 洗过的按片去重，重跑不会重复洗 —— **这就是现在唯一的"续干"机制** |
| 心跳 | `state/refine-心跳.json`（`上次检查 / 二层对话产出 / 待重洗`） | cron 一分钟一趟，看它"还在不在跑" |
| 洗不了的账 | `state/refine-待重洗.json` | 语料没了、三层也没原文的，不许静默当"洗过了" |
| 清洗看守 | `state/activity.json`（`任务结束/时间/问题`） | 模型思考期间别把二层清了 |

### ✗ 没有的（要新建）
| 缺口 | 现状 | 建议 |
|---|---|---|
| **运行内存库（在飞事件）** | 库里只有 `rag_chunks / search_corpus / search_hot`，**没有**记"正在洗哪一条、洗到第几段"的表 | 新表 `pipeline_flight`：`id / 来源 / 对话id / 段序号 / 状态(在飞\|成了\|失败) / 重试次数 / 起止时刻 / 产物hash` |
| **显式游标** | `state/refine-state.json` 里只有 `上次清洗` 一个时间戳，**没有"某文件洗到第几段"** | 游标交给上面那张表（按 `来源 + 段序号` 就能续） |
| **单对话 exec 计数** | `config/agent.json` 只有 `exec.max_rounds 4`（单任务），**没有**对话级闸 | 计数跟着对话走（web 用对话 id；CLI 进程内 + 落盘），上限 50 |
| 编排清单表 | 同上，库里没有 | `orchestra` 表（见 §4） |
| 编排 → 清洗管线 | refine 现在只扫 `corpus/hermes-history/`，**编排的产出它看不见** | 编排产出落成同款语料文件（原文备份），refine 的扫描目录加一个源即可 |

### 一句话
**"两层库 + 心跳 + hash 去重 + 洗不了的账" 都搞过了，能复用；缺的是"在飞的那张表"（运行内存库）和它的显式游标** —— 现在断电后靠"重扫一遍、按 hash 跳过"续，不是靠记账续。
