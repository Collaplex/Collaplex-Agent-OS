|---|---|---|---|---|
| 1 | 调用 | 模型发的命令 | — | — |
| 2 | 命令路由 | 命令 | 分派到「搜 / 取 / 截图」 | 命令不认识 → 回用法 |
| 3 | 闸门 | 本轮已用次数、字节数 | 放行 / 拦 | 被拦 → 回一句人话，不静默 |
| 4 | 真浏览器抓取 | URL 或查询词 | html ＋ 截图 ＋ 状态码 | 见第 4 节四类出口 |
| 5 | 错误分类 | 状态码 / 异常 | 四类之一 | 同上 |
| 6 | 程序清洗 | html | 标题 ＋ 正文段落 | 清洗空 → 走第 7 步的否分支 |
| 7 | 判定「清洗后有东西吗」 | 段落总字数 | 是 / 否 | 否 → 只回截图 |
| 8 | 切片 | 正文 | 切片 | 借 rag 的 `chunker.py`，不另写 |
| 9 | 去重 | 切片 | 新增 / 更新 | URL 归一 ＋ 正文指纹，**跨来源也去重** |
| 10 | 入热库 | 切片 | 写进 `search_hot` | 入库失败 → 回原因 |
| 11 | 检索 | 问题 | 最相关的若干段 | **只搜热库** |
| 12 | 返回结果 | 片段 | 原文片段 ＋ 链接 ＋ 截图 | 不改写、不总结 |

第 4 步的浏览器是**常驻**的，另配一个**延时看门狗**：闲置超过 5 分钟就杀掉（见第 6 节），下次要用再拉起。

**另外两条支路（原稿就有，保留）**

- `命令路由 → 浏览器渲染 → 出图 / 获取 html → 汇总`
- `汇总 --html--> 程序清洗`（并回主链）
- `汇总 --图片--> 返回结果`（直接回）

**skill.md 侧（模型侧）**

- skill.md 教模型先判该去哪个站，判完再发命令
- 模型还想继续用 → 再发命令，**单轮上限 100 次**

## 2. 数据面

### 热库 `search_hot` —— 检索只查这里

- 寿命：**24 小时**（我定的档）
- **热是一份**：不分来源，来源只是列（bing / 百度 / 直连 / 渲染）
- 列：`id / url / 域名 / 来源 / 标题 / hash / idx / text / embedding vector(1024) / 抓取时间 / 状态码 / 截图路径 / 热到什么时候`
- 索引：`unique(url 归一, hash)`、`hnsw(embedding)`
- **形状跟 `rag_chunks` 对齐**（`tier/hash/text/embedding vector(1024)`）→ 向量与检索算法整套复用 rag
- **截图跟 TTL 一起清**：热库里那条没了，它的截图也删

### 语料库 `search_corpus` —— 就是你说的「专门放搜索引擎语料的库」

- 寿命：**90 天 或 2GB**，先到先清最老（我定的档）
- 列：与热库同，另加 `首次抓到 / 最后抓到 / 命中次数`
- 去重：长期唯一（URL 归一 ＋ 正文指纹）
- 供后续人直接查（人也能用，不只是程序用）

### 为什么分两层

你说「检索只搜热的」→ 那就必须有个热的地方。
而语料库要长期留着给人复用 → 两者寿命不一样（24 小时 vs 90 天），挤在一张表里没法各自定 TTL。

### 下沉

抓取先入热库 → TTL 到期由**下沉任务**（cron）去重后并入语料库 → 热库里清掉。
跟项目里「二层热库 → refine 下沉冷库」是同一套路子。

## 4. 失败语义（四类出口）

| 情况 | 回什么 |
|---|---|
| 响应超时 | 「响应超时」＋ URL |
| HTTPS / 证书错 | 「HTTPS 错误」＋ URL |
| 其余失败：404 / 站点不存在 / 站点拒绝 | **具体报错**（带码或域名） |
| 抓到了但清洗后没内容 | **只回截图**，不硬塞空正文 |

前两类自成一类（本身就说不出更具体的），第三类才叫「具体报错」。
**「具体报错」是从抓取这一关出来的，不是从清洗出来的** —— 原稿没画这条，这是补的。

通用原则：取不到 / 清洗空 / 切片空 / 入库失败，四种都直接回一句带原因的话，**不重试、不静默**。

### 9.3 今天踩出来的坑（都已在代码里堵住）

1. **cn.bing.com 对长中文机构名会灌泛结果**：`浙江工业职业技术学院 绍兴` → 结果全是「浙江省」；
   `机器学习 入门` → 按「机器」查词典。**不是解析 bug，是 bing 自己的分词/相关性**，重排救不回。
   → 堵法：结果里**含核心词比例 <30%** 就**退回核心词（最长中文词）重查一次，谁对题用谁**。
   实测这一招在 5 个查询里 3 个明显变好、1 个平、1 个两个都烂（`collaplex` 本来网上就没东西）。
2. **URL 参数只带 `q` 与 `count`**：实测 `ensearch=1` 会让结果变成完全无关的（AutoCAD 那种）→ 毒药；
   `form=QBRE` / 带引号 / `mkt=` 无害也无用（我一度把它们当毒药 —— 其实是**连打把 profile 弄脏了**，冤枉的）；
   `www.bing.com` 明显更差（同一查询给出一堆电商活动页），所以默认走 cn、挂了才回落 www。
3. **浏览数据（profile）养脏后 bing 给泛结果**：同一查询连打 20 多次，对题率 **7/10 → 0/10**；
   **换新 profile 立刻回到 7/10**；HTTP 直抓在同一时刻仍是 7/10（同一查询两条路同时对照过）。
   → 堵法：`stop`（含看门狗杀进程）时**把 profile 一起清掉**（`wipe_profile_on_stop`）。
4. **Chrome 155 根本不发 `Page.domContentEventFired` / `loadEventFired`**（探针实测只有 `frameNavigated` 与 Network 系列）
   → 导航等待改成 `Page.lifecycleEvent` ＋ `dom_grace_seconds=3` 兜底；
   404 那页从 **28 秒 → 3.2 秒**。
5. **看门狗要连进程一起收**：只删 `watch.pid` 不杀进程会留**孤儿看门狗**，下次 `start` 又起一个
   → 两个看门狗盯同一个 chrome。`stop` 里先杀看门狗再收 chrome。
6. **`<title>` 在 `<head>` 里，而 `head` 是丢弃标签**：丢弃计数先于标题判断 → 标题永远是空的
   → `handle_data` 里先认标题再看丢弃计数。
7. **首页类页面「正文」天然很薄**（头条首页切出来 27 字，全是导航块）：不是 bug —— 首页没有正文段落。
   要看正文就取文章页；`--min 40` 能把导航词滤掉（百科那页 398 段 → 127 段，开头就是正文）。

### 10.2 百度只能 HTTP 直抓（真浏览器打百度是空页面）

四条路各打一遍（`~/.hermes/cache/scratch/baidu_probe.py`）：

### 10.4 第二刀踩出来的坑（都已在代码里堵住）

1. ★ **按站各退各的核心词**：合在一起判，bing 那堆泛结果会把整体拉低，对题率 **100% → 41%**。
   → `site_once` ＋ `search_site`：每站单独判「含核心词比例 <30%」再各退各的核心词（最长中文词）。
2. **百度只能 HTTPS 直抓**（见 10.2）—— 「必须真浏览器」只对 bing 成立。
3. **真浏览器 profile 会养脏**（第一刀就有，这里再确认）：`browser.json` 的 `wipe_profile_on_stop: true`。
4. **不许叫 `store.py`**：rag 也有一份同名件，pyright 会认成 rag 那份（报「没有 budget 这个属性」），运行时又是另一份
   → 改名 `corpus.py`，名字唯一，两边都不猜。
5. **诊断全走 stderr**：stdout 只放结果/JSON（不然 `--json` 被 `[落库] …` 污染，管道解析就炸）。
6. **别拿表名做 `regclass` 强转**：表不存在时抛 `relation "…" does not exist`，建表前的一次自检就把自己卡死
   → 查 `pg_class` / `pg_attribute` 按名字找。
7. **`metadata.json` 的 `needs.env` 只能写裸键名**（`["RAG_PG_DSN", …]`）；把说明写进括号 → 自检那条「声明的环境变量都在」必报缺。
8. **闸先扣再搜**（搜完再说超了等于没闸）；`--no-gate` 只给实验用。
9. **嵌入单条上限 4000 字**（`store.json` 的 `embed_max_chars`；rag 实测超了会把嵌入服务打挂）。
10. **PG 断了别慌**：`corpus.py` 连不上会自己重试 3 次（PG 重启那两秒不炸）。

2. 热库里的都是**测试数据**（bing 那次的 serp），可以随时 `清理` 掉；冷库空。

### 12.1 补了什么

| # | 缺口（设计图有、代码无） | 落在哪 | 怎么做的 |

### 12.3 这一刀踩出来的坑

1. **`isinstance(x, dict)` 收窄 `Any` → 类型检查报「部分未知」。** `json.loads` 出来是 `Any`，一 `isinstance` 收窄就变
   `dict[Unknown, Unknown]`，`.get()` 立刻被报 `reportUnknownMemberType`。别在原地硬辩，**把读配置这件事收进一个件**
   （`fetch.store_mb(key, default)`），调用方拿到的就是 `float`。★另一条 `fetch.store_mb 不是 fetch 的属性` 是 **LSP 缓存假报**，
   真跑 pyright 是 0 —— 类型报错也要拿真跑复核。
2. **凭记忆重写整个文件 = 自己造 bug。** 差点把 `CREATE TABLE` 的续行写成 `{}\"`（多一个转义引号 + 真换行，SQL 直接废）。
   `write_file` 的“先读过才让写”拦了一道，读回来才发现。**改文件先 `read_file` 拿真内容，再定点 `patch`。**
3. **向量服务 8199 是项目自带的 `vendor/llama.cpp`，不是 LM Studio。** `start_models.sh` 里主模型 8790 + 向量 8199；
   只想起向量那个就单独拉（`CUDA_VISIBLE_DEVICES=` 空 + `-ngl 0`，纯 CPU），**别顺手把主模型也拉起来占显存**。
   本机当时 8790 上已经有主模型在跑（老板/别的会话的），**不是我的，别动**。
4. **`kill` 拿到的 PID 可能是包装层。** 第一次 kill 报的 PID 停不掉服务；**按端口反查才准**：
   `ss -ltnpH | grep :8199` → `users:(("llama-server",pid=…))`。★`case` 模式里的字符类**别加引号** —— 加了就成字面量，
   会把自己那条命令行也匹配上（这一刀真踩了，扫到自己）。
5. **别对装着大索引的目录做宽 `grep`。** 一句 `grep -rn 8199 --include=*.json` 把 26 万字符的 `*-index.json` 灌进了上下文。
   要么先 `search_files` 限定路径，要么把 `*.json` 摘掉。
