# 路由模型：挑"这题该走哪条路" + ★ 一个反直觉的架构发现

对应老板新架构图 `diagrams/模型架构设计.drawio` 里的**「路由模型」**那一件。

老板的话："路由模型挑选的是需要激活哪些专家" —— 在我们的场景里，第一步能落地又能直接测的版本是：
**挑该用哪个 skill（走哪条路）**。数据全现成、0 元、CPU、不碰显存。

## 做法
- 输入：59 道题的 Qwen3-0.6B 隐层特征（复用 `习惯模型-特征.npz`，1024 维）
- 标签：题库 `skill` 字段 —— linux 22 / math 10 / file 2 / seek 1 / 空（不该动手）24
- 对照：`样本.jsonl` 里模型实际挑中的 skill
- 手写 softmax 回归 + 留一交叉验证

## 结果

| 判据 | 训练窄头 | 现有模型 |
|---|---|---|
| ① 五类混着挑方向（含「空」）| 37/59 = **62.7%** ✗ | 47/59 = **79.7%** |
| ② ★ **math（该算的题）单独认** | **10/10 = 100%** | 5/10 = **50%** |
| ③ 合并（math 题任一个认出就算）| **10/10** | — |

## 两条结论

### 1. ★★ 专件专训 ≫ 混着训 —— 老板图上"多个件"的设计被实测证实
同一批特征、同一个模型：
- **math 单独训 ⇒ 100%**
- 五类混着训 ⇒ 62.7%（反而比现有模型低 17 点）

原因：标签严重不均衡（linux 22 / 空 24 / math 10 / **file 2 / seek 1**），留一验证时
seek / file 这种只有 1~2 条的类**永远学不到**，还把别的类拖下水。
⇒ **架构上就该一件管一个判断**，一件一件训、一件一件验（这就是"多个件"的价值）。
⇒ 少类（file / seek）要**补样本**才有意义。

### 2. ⚠ 更正：math 头"100%"只是召回，**不能单用**（精确只有 62%）

| | 数 |
|---|---|
| 召回（该算的认出几题）| 10/10 = **100%** |
| **精确（它说要算的里面真有几题要算）** | 10/16 = **62%** ✗ |
| 误报 6 题 | 根分区还剩多少 / 谁占着 8789 端口 / 显卡温度多少显存还剩多少 / 水的化学式 / 一年有多少个月 / 两层库有什么区别 |

★ 误报的**全是"题里带数字／多少"的题** ⇒ 这个头学到的**不是"数学"，是"问句里有数量词"**。
拿它用 = 把 linux 题当算数题 ⇒ **等于把现有模型的错（题 23/43 该 math 却查机器）换个方向犯** ✗

⇒ 结论：**它不能单用**；而且**路由这一件我还没做出来**（整体 62.7% < 现有模型 79.7%）。
⇒ 根因是**样本太少 + 类别不均衡**（file 2 条 / seek 1 条）⇒ 下一步该做的是**补样本**，不是继续调模型。

★ 教训：**单类召回数字会骗人** —— 100% 召回 + 62% 精确 = 用起来一半是错的。
判据必须报**完整混淆**（TP/FP/FN/TN）或至少召回 + 精确，不能只报好看的那一半。

## 顺带抓到的结构关系（决定件的先后）
现有模型挑错的 9 题**分成两类**：
- **6 题是"压根没动手"**（19/38/39/42/44/45）⇒ 这是**习惯模型**漏的同一批
- **3 题是"动了但走错"**（题 1 挑了 rag 而标 seek；题 23「算力是多少」、题 43「注水」该用 math 却去查机器）

⇒ **习惯在前、路由在后，两件是串联的**：习惯先决定"要不要动"，路由再决定"走哪条"。
⇒ **两个件不能省成一个**（又一次证明多件互补）。
