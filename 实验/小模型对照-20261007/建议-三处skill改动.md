## ① `config/skills/exec.md` —— 加两节（回答组织 + 别钻牛角尖）

加在文件末尾：

```markdown
## 回答怎么组织（★ 必须）

回答分两段，顺序固定：

1. **先给结论** —— 数字 / 型号 / 做到了没做到 / 一句话答案。这段是给人看的，也是以后被检索的。
2. 最后再单起一段 `# 过程`，里面才写"试过什么、被拦了、输出了什么"。

不这么写的后果：过程混在正文里，下次这段会被当成内容读回去，
它就照着"再试一遍"的调子接着试 —— 所以**过程和结论必须分开**。

## 别钻牛角尖（★ 硬规则）

同一条路连着被拦 / 连着失败 **2 次**，就**停手换思路**。

- 换的是**思路**，不是写法：
  - ✅ 换思路：先看清现状（`ls` / `du` / `df`）再决定 → 换个手段（skill 里另一条命令）→ 直接说"这条我不能做，得你来"
  - ❌ 换写法（**不算换思路**）：`rm -rf /tmp` → `rm -rf /tmp/*` → `find /tmp -delete` → `sudo find /tmp -delete`
- 判断标准：**新命令和上一条是不是同一族**（都在删 / 都在改权限 / 都在重启）。同族 = 没换思路。
- 连着 2 次还在同族里，就必须停下来，把"做不了 + 为什么 + 替代办法"写进结论，别再试第三次。
```

## ② `config/skills/judge.md` —— 补对比例子（治"短语题"漏判）

加在"★ 判据是「这件事的结果要不要落在这台机器上」"那节后面：

```markdown
### 短句不等于"不用动"（★ 实测漏得最多的一类）

判断**不看句子长短**。"现在几点了"只有 5 个字, 但答案在机器上 → 需要。

| 问的 | 判 | 为什么 |
|---|---|---|
| 现在几点了 | need true | 时间要从机器上读（`date`） |
| 时间怎么换算、时区怎么算 | need false | 问方法，常识 |
| 两车相向而行 | need true | 是要算出一个数 —— 缺条件就先问缺什么，或按通用解算 |
| 加盐提浓度 | need true | 同上，是要一个数 |
| 帮我看看还有多少空间 | need true | 答案在机器上 |
| 空间不足会怎样 | need false | 问后果，常识 |

★ 这几条是实测里**每次都漏**的（`现在几点了` / `两车相向而行` / `加盐提浓度` 各 5/5 全漏），
它们共同点是**句子短、没实体词** —— 越是这种越要按"要不要落在机器上 / 要不要出一个数"判。
```

在"执行步骤"后加一节：

```markdown
## 额外：经验条（★ 只从失败/被拦里提炼）

这次问答里如果有**被拦下、试错、走不通**的地方，额外提炼"经验"——但只写**教训**，
**一个字的过程都不写**：

- ✅ 好的经验条（独立、可用、无过程）：
  - "这台机器上不能用 `rm -rf` 或 `find -delete` 清 /tmp，程序会拦；要清只能逐一点名删"
  - "这台机器的桌面目录是 `~/桌面`（不是 `~/Desktop`）"
  - "看 C/C++ 文件不能用 carve（它只认 Python），要用 head/sed/grep"
- ❌ 不许写成这样（这是过程，不是经验）：
  - "我先试了 rm -rf /tmp 被拦，又试了 rm -rf /tmp/* 被拦，最后试了 sudo 还是被拦"
  - "尝试了 4 种方法都没成功"

格式与「知识」一致，一起放进同一个数组（程序按"独立可读"嵌向量入库）；
实在没有失败/踩坑就**不产出经验条**，不许硬凑。
```
