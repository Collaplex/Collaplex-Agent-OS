# 你负责定时 —— 到点了把话带回来

本体就两样：**闹钟**（说时刻：「下午三点」）和**倒计时**（说时长：「30 分钟」）。到点做的事只有一件：**把提醒交回主 agent**。

## 红线（这几条最要紧）

- **不许自己数时间**：到没到点只能由引擎的表说了算。不许说「我算着还剩三分钟」，也不许替老板盯着。
- **只提醒，不动手**：到点只把话带回来。真要做事（关模型、删文件、发消息）由主 agent 收到提醒后另挑 skill —— 这个 skill 不碰不可逆操作。
- **不悄悄降级**：阻塞式超 180 分钟算**条件不合法**，要把「改短」还是「改非阻塞」摆出来让主 agent 定，不许自己改成非阻塞糊过去。
- **四项判据缺哪条报哪条**：时间 / 提醒什么 / 阻塞还是非阻塞 / 是否超上限 —— 缺什么就把 `缺` + `可选` 原样转给老板，别猜一个填上。
- **收到提醒别再定一个**：到点那次提醒是「该干那件事了」的信号 —— 直接回话 / 直接办，别再 register 一遍（真机实测模型爱多此一举）。

## 干活三步

1. **挑这条命令**（原话照抄进参数，别自己改写时间词）：
   - `.venv/bin/python skill/timer/main.py register "<老板原话>"`
   - 想让它等你，原话里就得有「等着 / 就在这」；想先走就得有「提醒我 / 先去忙」。判不出来命令会告诉你缺哪条。
2. **看输出**：
   - 退出码 0：登记好了，输出里有 `[id xxxx] 倒计时 · 还有 30 分 00 秒`（闹钟才会带钟点：「10-09 15:20:00（还有 …）」）—— **照抄**给老板。
   - 退出码 1：`[条件不足]` —— 缺项和可选项按条列出来，**原样**转给老板（别自己替他选）。
3. **这一轮怎么收尾**：
   - **阻塞式**：框架就在这一轮里等，`过程` 面板里一格原地读秒，到点把提醒喂回来 —— 你只管接着答。
   - **非阻塞式**：说一句「定好了，到点我提醒你」，**这一轮就结束**；到点那次提醒会出现在你下一轮的开场。

## 其它动作

| 动作 | 干嘛 |
|---|---|
| `list` | 看现在挂着几条（带 id / 到点 / 阻塞还是非阻塞） |
| `cancel <id>` / `cancel --最近` | 撤掉一条（老板说「不用了 / 取消」就用它） |
| `take --json` | 把到点的取出来（框架每轮开场调，人不用管） |
| `arm` | 进程起来时重挂一次（框架调，人不用管） |
| `status` | 表在哪 / 线程活没活 / 挂了几条 |
| `selfcheck` | 自检：配置能读 / 表能读 / 时长解析对不对 |

## 边界

- **上限**：阻塞式最高 **180 分钟**（`config/timer.json`），一次最多挂 **20 条**。
- **不是 crontab**：它是**进程内的、会话语义**的一次性闹钟 —— 进程不在就不响。系统的周期任务归 crontab（比如清洗那条），两回事。
- **跨重启**：表落**冷库**（PG 表 `timers`，按进程键分行：web / cli 各一行），启动时读回来重挂；发现的**过期条目补一次**，并标明「这条是补的，早就该响」。
- **web 与 CLI 各一张表**：两个进程同时开着，提醒只回它自己那个进程。
- **说人话的到点**：提醒固定是 `⏰ 你定的闹钟到了：<原话>`。

## 例子

```
> 30分钟后提醒我关火，我先去忙别的
  register "30分钟后提醒我关火，我先去忙别的"
  → [id 4f2a9c11] 倒计时 · 还有 30 分 00 秒        # 非阻塞, 这一轮说完就完

> 一分钟倒计时，就在这等着
  register "一分钟倒计时，就在这等着"
  → [id 8b1d3e70] 倒计时 · 还有 1 分 00 秒        # 阻塞, 过程里读秒到点

> 下午三点叫我起来
  register "下午三点叫我起来"
  → [条件不足] 还缺: 阻塞还是非阻塞 —— 要我等在这儿, 还是先放我走
    能挑的: 阻塞: 加「等着」「就在这」; 非阻塞: 加「提醒我」「先去忙别的」
    （原话里已经有「提醒我 / 先去忙」的，就直接按非阻塞走，不用再问）

> 不用了，取消刚才那个
  cancel --最近
  → 撤了: [id 4f2a9c11] 30分钟后提醒我关火，我先去忙别的
```


## 长活怎么办: 起作业

要跑的东西**一轮里等不完**(脚本、抓取、编译、重洗语料…)别在这一轮里干等, 起成「作业」
丢后台, 等它跑完再把结果收回来 —— 这就是「延时让活跑完, 然后看结果」。

```bash
./.venv/bin/python 作业.py 起 "命令原文" "给人看的说明"   # 回一个活号
./.venv/bin/python 作业.py 查 <活号>                       # 在跑 / 跑完(退出码) / 失败 + 日志尾
./.venv/bin/python 作业.py 等 <活号> [--上限秒 30]          # 等到它跑完(每秒读秒), 或只看一眼
./.venv/bin/python 作业.py 列                              # 起过的活
./.venv/bin/python 作业.py 停 <活号>                        # 半路不要了
```

★ **跑完不用你盯着**: 下一轮开场时框架会自动把「跑完的活 + 退出码 + 日志尾」当开场话交给你
(形如 `[作业] 重洗语料（跑完·退出码 0，跑了 12 分 3 秒）` 后跟日志尾)。所以顺序是
**起活 → 去干别的(或等) → 下一轮看结果**, 不要在这一轮里 sleep 死等。
★ 账在 `state/作业.json`、日志 `logs/作业-<号>.log` —— 进程重启也读得回来, 不会漏。
★ 说明字段写清「这件活是干什么的」: 交付时主 agent 就靠它认出这是哪件活。
★ 日志尾一律用 Python 读文件（别用 shell 的日志夹具），退出码由活自己写进 `.退出`。
